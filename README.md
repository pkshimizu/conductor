# conductor

要件（GitHub Issue）を渡すと、テスト役・実装役・レビュー役の Claude Code を順に動かし、CI を通してマージまで進める開発エージェント。

開発中（Lv1）。

## 動かし方

```
conductor check [フォルダ]   設定を点検する
conductor start [フォルダ]   常駐して Issue を進める
```

- `poll_interval`（既定は 90 秒）ごとに GitHub Project を確かめ、作業中の Issue を1段階進めます。作業中の Issue が無ければ Ready 列から番号の小さいものを1件拾います。
- 作業中に数えるのは1件だけです。承認待ちの Issue は数えず、毎回 PR のコメントだけを確かめます。
- PR が main と衝突したら、実装役に差し戻して直させます（差し戻しの上限には数えません）。
- 同じ Issue が3回続けて失敗したら Blocked 列に移し、`github.notify` の人をメンションします。
- Blocked にするとき（続けての失敗・差し戻しの上限・テスト役や実装役・レビュー役の異議・テスト役が書けなかったとき・入口確認の書き漏れ）は、どの場合も、窓口（`chat`）を使うなら Issue でメンションせず Discord のスレッドで確かめます（「止まったときのスレッド」）。
- Ctrl+C を受けたら、今の段階を終えてから止まります。
- 進み具合の記録は `~/.conductor/state/<owner>__<repo>.db` に置きます。止めて再開しても続きから進みます。要件ごとの進み具合（状態・質問の数・仕様の PR・作業用 Issue とその順番）と、チャンネル・スレッドごとの「どこまで読んだか」も同じファイルに残します。前の版で作ったファイルは、記録を残したまま要件用の表が足されます。

## 管理画面

`conductor start` は同じプロセスから管理画面も配信し、起動したときに`管理画面: http://127.0.0.1:<ポート>/` をログに出します。

- ポートは起動ごとに空いているものを使います。127.0.0.1 だけで待ち受けるので、別の PC からは開けません。
- 画面は左にメニュー（ダッシュボード・タスク一覧・設定）、上にリポジトリ名・Project 番号・稼働状態（動作中・待機中・停止中）・言語の切り替えを出します。タスク詳細と設定の中身はこれから作ります。
- ダッシュボード（`/`）には、人の判断を待っている Issue（Blocked の列。止まった理由・止まった日時・止まった段階）、処理中の Issue（番号・タイトル・ブランチ・進み具合・動いている役・今の段階の経過時間・差し戻しと異議の回数）、稼働状況（最後に GitHub を確認した時刻・次の確認までの秒数・確認の間隔 `poll_interval`・マージ方法 `merge.approval`）、GitHub Projects の列ごとの件数を出します。経過時間は記録に残した段階を始めた時刻から数えるので、再起動しても正しく出ます。
- タスク一覧（`/tasks`）には、Project のすべての Issue（閉じた Issue も）を表で出します。列は Issue（番号）・タイトル・列・途中の段階・差し戻し・異議・PR（マージ済みならそう示します）・更新日時です。列（すべて・Ready・Done など。選択肢ごとに件数つき）と、番号かタイトルの一部で絞り込めます。行をクリックするとタスク詳細（`/tasks/<番号>`）を開きます。列は GitHub Projects から、回数・段階・PR は記録から読みます。
- 稼働状態とダッシュボード・タスク一覧の内容は再読み込みしなくても変わります（`/api/events` の SSE で知らせます）。言語はブラウザに覚え、配色は PC の設定（ライト・ダーク）に従います。
- 画面のソースは `web/`（React ＋ Vite）にあり、`npm run build` で `dist/admin/` にビルドして conductor に同梱します。

## 対象リポジトリに置くもの

```
.conductor/
  config.yaml        設定
  tester/*.md        テスト観点（テスト役が参照する）
  implementer/*.md   実装ルール（実装役が参照する）
  reviewer/*.md      レビュー観点（1ファイルにつき1人のレビュー役が並列で確認する）
  specifier/*.md     仕様化の決まり（仕様化役が参照する。窓口を使うときだけ）
  decomposer/*.md    分解の決まり（分解役が参照する。窓口を使うときだけ）
  knowledge/*.md     他の機能にも使える方針（仕様化役が書き足す）
```

- 各フォルダの .md はファイル名の順に読みます。フォルダが無ければ追加の指示なしで動きます。
- レビュー役は観点ごとに並列で動き、1つでも差し戻しなら差し戻し、異議があれば異議、全員が承認ならマージします。
- 同時に動かすレビュー役の数は `limits.reviewers`（既定 3）で決めます。
- 役が書く文章（要約・指摘・質問）の言語は `language`（既定 `日本語`）で決めます。例: `language: English`。conductor が書く定型文は日本語のままです。

## 窓口（chat）

要件の受け取りと人への質問をチャットで行うための設定です。Discord とは PC から REST API（v10）を読みにいくだけ（ポーリング）でやりとりし、外から PC へ接続する口（Webhook・Gateway）は作りません。

```yaml
chat:
  type: discord # 今は discord のみ
  channels:
    requirements: "1000000000000000001" # 要件のチャンネル ID
    questions: "1000000000000000002" # 質問のチャンネル ID
    notices: "1000000000000000003" # お知らせのチャンネル ID
  allowed_users: # 許可する人（ユーザー ID）
    - "2000000000000000001"
```

- ID は数字だけでも文字列（`"..."`）で書きます。
- トークンは config.yaml に書かず、環境変数 `CONDUCTOR_DISCORD_TOKEN` で渡します。`chat` を書いてトークンが無ければ、`conductor start` は起動しません。
- `chat` を書かなければ窓口を使わず、GitHub だけで動きます。
- 読むのは要件・質問・お知らせのチャンネルと、その下のスレッドの投稿だけです。ほかのチャンネルの投稿は捨てます。
- 2000 文字を超える文は、分けて書き込みます。

### 要件の受け取り

`conductor start` は確認のたびに、作業中の Issue の処理とは別に、要件チャンネルの新しい投稿を受け取ります。

- 許可した人（`allowed_users`）の投稿1つを要件1件とします。2回投稿すれば2件です。要件への書き足しは、その要件のスレッドに書いてください。
- 受け取ると、質問チャンネルに要件のスレッドを作り、要件の本文を引用して書きます。要件は仕様化中として記録します。
- 許可していない人の投稿と Bot 自身の投稿は無視します。
- どこまで読んだかは記録に残すので、再起動しても同じ投稿を二重に受け取りません。
- 受け取りに失敗しても Issue の処理は止めず、次の確認で続きから読みます。

### 仕様化

受け取った要件（仕様化中・承認待ち）は、確認のたびに仕様化役（Claude Code）が1回分ずつ進めます。

- 仕様化役は毎回新しく起動し、要件とスレッドのやり取りをすべて渡します。
- 疑問があれば、番号とおすすめの答えをつけて1つの書き込みにまとめてスレッドに書きます。全部おすすめでよければ「全部おすすめでよい」と1行で返せます。番号ごとに答えてもかまいません。
- 疑問がなくなると、仕様を対象リポジトリの `docs/specs/` に、他の機能にも使える方針を `.conductor/knowledge/` に書き、要件ごとのブランチ（`conductor/spec-<要件の投稿 ID>`）1本の PR にして、要約と PR のリンクをスレッドに書きます。方針に従って自分で決めた点は、仕様に「方針○○により判断」と書きます。
- 要約のあとに ✅ 以外を書くと修正の依頼として扱い、同じ PR を直して要約を書き直します（✅ による承認の判定は別に行います）。
- 前回の確認より後に許可した人の書き込みが無ければ何もしません。返事が来なくても催促しません。
- 質問の数は要件ごとに記録に残します。
- 仕様化役への追加の指示は `.conductor/specifier/*.md` に書きます。許可する操作は `roles.specifier.allow` で足せます。

### 仕様の承認

承認待ちの要件は、確認のたびに仕様の承認を確かめます。判定は LLM に任せず、プログラムで行います。

- 最新の要約（仕様化役が最後に書いた要約）に、許可した人（`allowed_users`）が ✅ のリアクションを付けると承認です。
- 許可していない人の ✅、書き直す前の古い要約への ✅、✅ 以外の絵文字は承認として扱いません。
- 承認されたら仕様の PR の CI を確かめ、合格していればマージし、スレッドをアーカイブしてロックして、要件を分解に進めます（作業中にします）。
- CI が失敗していればマージせず、理由をスレッドに書いて待ちます（同じ要約については1回だけ書きます）。CI が通れば、✅ を付け直さなくても次の確認でマージします。CI が実行中なら書き込まずに待ちます。

### 分解

分解に進めた要件（作業中で、作業用 Issue がまだ無いもの）は、承認を確かめた後に分解役（Claude Code）が作業用 Issue に分けます。

- 分解役には、仕様の PR で変えた `docs/specs/` のファイルを読ませます。分解役は各 Issue の中身（目的・受け入れ条件・画面の URL と文言・対象外）と順番（先に済ませる Issue）を JSON で返すだけで、Issue の作成やファイルの書き込みはしません（読むだけの操作しか渡しません）。
- conductor は各 Issue の本文を入口確認と同じ見出し（`## 目的`・`## 受け入れ条件（AC）`・`## 画面の URL・文言`・`## 対象外`）に `## 先に済ませる Issue`（`#番号`）と `## 仕様`（仕様ファイルへのリンク）を足して組み立て、入口確認と同じ点検をしてから、先に済ませる Issue から順に作って Project に追加します。列は動かしません（Ready に移すのは別の段階です）。
- 作業用 Issue の番号は作業の順番（先に済ませるものが前）で記録に残し、Issue の一覧（`#番号`・タイトル・URL）をその順にスレッドに書きます。一覧の承認は取りません。
- 書式の誤り・無い Issue を先に済ませる Issue に指したもの・順番の循環があれば、Issue を1件も作らずに誤りを示して分解役にやり直させます。やり直しは `limits.rejections` 回までで、それでも直らなければ理由をスレッドに書いて要件を止めます（状態 `blocked`。以後は分解しません）。
- 分解役への追加の指示は `.conductor/decomposer/*.md` に書きます。許可する操作は `roles.decomposer.allow` で足せます（書き込みとコマンドの操作は足しても拒否します）。

### 着手と完了の知らせ

分解した要件（作業中で、作業用 Issue があるもの）は、確認のたびに作業用 Issue の様子を GitHub から読みます。

- 先に済ませる Issue（本文の `## 先に済ませる Issue` に書いた `#番号`）の PR がすべてマージされた Issue を `github.columns.ready` の列に移します。移すのは列が未設定（Project に追加しただけ）の Issue だけで、Ready・作業中・Done・Blocked の Issue は動かしません。Ready に移した Issue は、ふだんの Issue の処理で1件ずつ進めます。
- 「マージされた」は、その Issue を閉じる PR（`Closes #番号`）がマージ済みであることです。
- 要件の作業用 Issue がすべてマージされたら、お知らせチャンネルに要件の完了（要件の本文の最初の行と、マージした PR の `#番号`・URL の一覧）を書き、要件を完了（状態 `done`）にします。以後は確かめません。
- 要件の受け取り・仕様化・承認・分解・着手の確認は、Issue の処理と同じ確認の中でどれも進めます（Issue の作業中でも、別の要件の質問は進みます）。
- 作業用 Issue の1件が Blocked のときは、その Issue を先に済ませる Issue にしている Issue だけを待たせ、関係のない Issue は Ready に移して進めます。

### 止まったときのスレッド

窓口を使うとき、Issue を Blocked にしたら（どの理由で止めた場合も）、Issue でのメンションに代えて Discord のスレッドで人に対応を確かめます（Issue には止まった理由をメンションなしで書きます）。

- 次の確認で、質問チャンネルに Issue ごとのスレッドを1つ作り、止まった理由（最後のエラー・最後の指摘・異議の質問・本文の書き漏れなど）と Issue へのリンクを書いて、許可した人（`allowed_users`）にメンションします。
- 許可した人がスレッドに方針を書くと、次の確認で方針を Issue にコメントで書き写し、Issue を `github.columns.ready` に戻して、スレッドをアーカイブします。
- 人が GitHub で直接 Issue を Blocked の列から出したら（Ready に戻すなど）、次の確認でスレッドをアーカイブします。
- Discord や GitHub との通信が途中で落ちても、次の確認で続きからやり直します（方針を二重に書き写しません）。
- どの Issue のスレッドか・止まった理由は記録に残すので、再起動しても同じ Issue のスレッドを作り直しません。
- `chat` を書かなければ、今までどおり Issue で `github.notify` の人をメンションします。

### 仕様の作り直し

止まった Issue が要件の作業用 Issue のときは、スレッドに書かれた方針をそのまま書き写す前に、仕様化役に方針と仕様（前の仕様の PR の `docs/specs/` のファイル）を渡して、仕様の変更が要るかを判断させます。

- 変更が要らなければ、上のとおり方針を Issue に書き写して `github.columns.ready` に戻し、スレッドをアーカイブします。
- 変更が要れば、仕様化役が直した `docs/specs/`・`.conductor/knowledge/` をブランチ（`conductor/respec-<Issue 番号>-<スレッド ID>`）にコミットして仕様の PR を作り、要約と PR のリンクをスレッドに書いて ✅ を待ちます。その間 Issue は Blocked のままです。
- その要約に許可した人が ✅ を付けると、次の確認で仕様の PR の CI を確かめてマージし、変更点（要約）と方針を Issue にコメントで書き写して `github.columns.ready` に戻し、スレッドをアーカイブします。CI が失敗していればマージせず、理由をスレッドに1回だけ書いて待ちます。
- 作業用 Issue の作り直し・追加はしません（変更点は Issue への書き写しで伝えます）。

## マージの承認

```yaml
merge:
  approval: human # human（既定）または auto
```

- `human`：レビュー役が承認したら PR でメンションして待ちます。書き込み権限のある人が PR に `/conductor approve` とコメントするとマージします。
- `/conductor reject`：承認待ちになった後のコメント（行へのコメントを含む）を指摘として実装役に差し戻します。差し戻しの上限回数には数えません。
- `auto`：人の確認なしに、レビュー役が承認したらすぐマージします。
