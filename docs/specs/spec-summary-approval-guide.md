# 仕様の要約の書き込みに、✅ で承認できることを書く

## 要件

> 要件を確認して、仕様まで作成できたときに、Discord二投稿する報告メッセージに ✅ をつけることで承認できることを記載したい

## 今の動き

- 仕様化役が仕様を書く（直す）と、指揮役が要件のスレッドに要約の書き込みを出す（`src/specifier.ts` の `summaryMessage`）。
- 承認は、許可した人（`config.chat.allowed_users`）が**最新の要約の書き込み**に付けた ✅ のリアクションで判定する（`src/spec-approval.ts`）。承認されると、仕様の PR の CI が合格していればマージし、作業の分解に進み、スレッドをアーカイブしてロックする。
- ところが要約の書き込みには、✅ で承認できることが書かれていない。今の最後の行は「直してほしい点があれば、このスレッドに書いてください。」だけである。
- 作り直した仕様の要約（`src/respec.ts` の `respecSummaryMessage`）には、すでに ✅ の案内がある。これは変えない。

## 仕様

### 1. 要約の書き込みの終わりの文言を変える

`summaryMessage` の最後の行「直してほしい点があれば、このスレッドに書いてください。」を、次の1行に置き換える（方針「承認の案内」により判断）。

```
この内容でよければ、この書き込みに ✅ を付けてください。仕様の PR をマージし、作業の分解に進みます。直してほしい点があれば、このスレッドに書いてください。
```

- ✅ の文字は手で書かず、`APPROVAL_MARK` を埋め込む（方針「承認の案内」により判断）。
- 「仕様を書きました。」と「仕様を直しました。」のどちらの要約でも同じ文言にする。承認の判定は最新の要約だけを見るので、直した後は新しい要約に付ければよく、「この書き込みに」で足りる。

書き込みの全体は次の形になる。

```
仕様を書きました。（または 仕様を直しました。）

<要約>

PR: <仕様の PR の URL>

この内容でよければ、この書き込みに ✅ を付けてください。仕様の PR をマージし、作業の分解に進みます。直してほしい点があれば、このスレッドに書いてください。
```

### 2. 変えないもの

- 1行目（`仕様を書きました。`／`仕様を直しました。`）と `PR: ` の行。`isSummaryMessage` がこれで要約の書き込みを見分け、`latestSummary` が承認を確かめる書き込みを選んでいる（方針「承認の案内」により判断）。
- 承認の判定（`src/spec-approval.ts`）、修正の依頼の扱い（✅ だけの書き込みは修正の依頼にしない）。
- 疑問の書き込み（`questionsMessage`）、仕様のファイルが書かれなかったときの書き込み（`unwrittenMessage`）。承認するものが無いため案内を入れない。
- `respecSummaryMessage`。

## 受け入れ条件

1. `summaryMessage(要約, PR, false)` と `summaryMessage(要約, PR, true)` のどちらの書き込みにも、「この書き込みに ✅ を付けてください」と、承認すると仕様の PR をマージして作業の分解に進むことが書かれている。
2. 同じ書き込みに、直してほしい点はこのスレッドに書けばよいことも書かれている。
3. 書き込みの1行目は今までどおり `仕様を書きました。`／`仕様を直しました。`で、`PR: <URL>` の行がある。`isSummaryMessage` はこの書き込みを要約と判定する。
4. 仕様化役が仕様を書いた後、スレッドに出た要約の書き込みに許可した人が ✅ を付けると、今までどおり承認として扱われる（CI が合格なら仕様の PR がマージされる）。
5. lint・整形・型・テスト・ビルドが通る。
